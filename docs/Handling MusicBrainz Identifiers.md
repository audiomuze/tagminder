# Handling MusicBrainz Identifiers

## The Core Problem

When building a music server, you need **canonical identification** for contributors (artists, composers, engineers, producers, etc.) to enable linking across your music collection. However, not all contributors exist in MusicBrainz, and they may be added later.

The central challenge: How do you handle contributors that:
- Don't have corresponding MBIDs in your file tags?
- Don't exist in MusicBrainz yet?
- May appear in MusicBrainz in the future?
- Are part of multi-artist tags with mismatched tag counts?

---

## Architectural Strategy

### 1. Synthetic UUID Generation

> **Core Principle:** Decouple **Credit Identities** (who is written in file tags) from **Canonical Entities** (the actual database row).

When your server encounters a contributor name **without** a corresponding MBID tag, generate a permanent, deterministic identifier using **UUID Version 5**.

**Why UUIDv5?**
- Unlike random UUIDs (v4), UUIDv5 is generated by combining a fixed namespace with a string (the artist name)
- The same artist name will **always** produce the same UUIDv5
- If the same unmapped artist appears across different albums/tracks, they're instantly linked to the same local entity

---

### 2. Solving the Multi-Artist Tag Alignment Dilemma

An audio file might have **three names** in the `ARTIST` tag but only **two MBIDs** in the `MUSICBRAINZ_ARTISTID` tag.

**Solution: Positional and Text-Based Alignment**

Your scanner must parse raw string arrays and realign them using a fallback hierarchy:

1. **Strict Positional Matching:** If the number of names matches the number of MBIDs exactly, map them 1:1 by array index.
2. **MusicBrainz Search Mapping:** If counts mismatch, check if any text names are found in the existing MBID fields (e.g., as aliases or sub-components).
3. **Synthetic Generation:** For any leftover text name that cannot be confidently mapped, generate a UUIDv5.

---

### 3. The Data Model (The "Bridge" Schema)

Do **not** store MBIDs directly as the sole primary key. Instead, use an internal `contributor_id` that can map to either a real MBID or a synthetic UUID.

#### Table: `contributors`

Holds the canonical "Human/Group" profile on your server.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PRIMARY KEY | Can be a real MBID or a local UUIDv5 |
| `display_name` | VARCHAR | NOT NULL | The primary name used in the UI |
| `is_canonical` | BOOLEAN | NOT NULL | TRUE if verified in MusicBrainz, FALSE if synthetic |
| `resolved_to_id` | UUID | NULLABLE | Points to the new MBID once merged |

#### Table: `contributor_aliases`

Maps all discovered text variations to the central ID.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `alias_name` | VARCHAR | PRIMARY KEY | The exact string found in file tags (e.g., "Jon Doe") |
| `contributor_id` | UUID | FK → contributors.id | The ID this text currently maps to |

---

### 4. The Resolution Lifecycle (Auto-Healing)

When a user adds an artist to MusicBrainz externally:

```
[File Tagged: "John Smith" (No MBID)]
   ➔ System generates UUIDv5: uuid_smith_123
   ➔ Status: is_canonical = FALSE

[Months Later: Artist added to MusicBrainz, files re-tagged with MBID mbid_smith_999]
   ➔ Scanner reads mbid_smith_999
   ➔ System looks up alias "John Smith" ➔ Finds uuid_smith_123
   ➔ System Updates: uuid_smith_123.resolved_to_id = mbid_smith_999
```

**Critical:** When `resolved_to_id` is populated, do **not** delete the old synthetic ID. Deleting it breaks historical play counts, playlists, and user favorites.

---

### 5. Exporting for External Resolution

Because synthetic artists are explicitly flagged (`is_canonical = FALSE` and `resolved_to_id IS NULL`), build a "Data Integrity" dashboard in your server UI.

Generate a clean CSV export:

```sql
SELECT display_name, id AS synthetic_uuid
FROM contributors
WHERE is_canonical = FALSE AND resolved_to_id IS NULL;
```

Users can take this list, add missing contributors to MusicBrainz, re-tag their files with Picard, and your server will automatically merge the data on the next library scan.

## Working with SQLite and Polars

All work is SQLite-based, with data held in memory in Polars dataframes after reading from the database. This means data may be the result of queries rather than simply lifting tables into RAM.

### Example: AMG Artists Table

```sql
CREATE TABLE amg_artists (
    mnid TEXT PRIMARY KEY NOT NULL,
    artist_input TEXT NOT NULL DEFAULT '',
    allmusic_artist TEXT NOT NULL DEFAULT '',
    allmusic_url TEXT NOT NULL DEFAULT '',
    name_similarity REAL,
    active TEXT NOT NULL DEFAULT '',
    born_date TEXT NOT NULL DEFAULT '',
    born_place TEXT NOT NULL DEFAULT '',
    biography_html TEXT NOT NULL DEFAULT '',
    enrichment_status TEXT NOT NULL DEFAULT 'stub',
    first_seen_utc TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_seen_utc TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_enriched_utc TEXT,
    last_source_mode TEXT NOT NULL DEFAULT '',
    raw_payload_json TEXT NOT NULL DEFAULT '{}',
    CHECK (length(trim(mnid)) > 0),
    CHECK (lower(mnid) GLOB 'mn[0-9]*'),
    CHECK (enrichment_status IN ('stub', 'partial', 'complete'))
);
```

### Example: AMG Artist Aliases Table

```sql
CREATE TABLE amg_artist_aliases (
    mnid TEXT NOT NULL,
    value TEXT NOT NULL,
    first_seen_utc TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_seen_utc TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (mnid, value),
    FOREIGN KEY (mnid) REFERENCES amg_artists(mnid)
        ON UPDATE CASCADE ON DELETE CASCADE,
    CHECK (length(trim(value)) > 0)
);
```

## The Namesake Problem

A **namesake problem** occurs when two entirely different humans share the exact same name (e.g., two session musicians named "John Smith").

**The Risk:** Generating a simple UUIDv5 based only on the text name would accidentally merge both people into the same local profile.

### Contextual Disambiguation Strategy

Make synthetic UUIDv5s **contextual** by hashing the name combined with disambiguating context (album MBID or primary band name):

```
❌ Instead of:
   UUIDv5(Namespace, "John Smith")

✓ Use:
   UUIDv5(Namespace, "John Smith" + "album_mbid_xyz")
```

### Namesake UI Workflow

When the server encounters a namesake with no explicit MBID tag:

1. Scanner recognizes "John Smith" is a known namesake
2. Provisions a temporary, context-bound synthetic profile
3. Places item on "Needs Resolution" queue in UI
4. User sees: "We found 'John Smith' on the album Blue Sky. Is this:"
   - **Choice A:** John Smith (Jazz Trumpeter from New York) — MBID A
   - **Choice B:** John Smith (British Punk Guitarist) — MBID B
   - **Choice C:** A completely different John Smith — Promotes to permanent synthetic

Include context: **Album Artist + Album name + MusicBrainz disambiguation field** to help users distinguish.

## Immutable Track Identity

A key architectural principle: **every user audio file has a UUIDv7** called `track_uuid` that is immutable once written to tags.

**Why this matters:**
- Completely decouples physical file paths and volatile text tags from engagement data
- Serves as the ultimate anchor for play history, playlists, and user favorites
- Turns a messy tag-matching problem into a permanent, self-healing state machine

With `track_uuid`, a user's **manual namesake decision survives tag rewrites and server refreshes forever**.

### User Disambiguation Overrides Table

```sql
CREATE TABLE user_disambiguation_overrides (
    track_uuid TEXT NOT NULL,         -- The immutable file ID (UUIDv7)
    raw_tag_name TEXT NOT NULL,       -- The exact text string from the file tag
    assigned_mbid TEXT NOT NULL,      -- The specific MBID the user picked
    PRIMARY KEY (track_uuid, raw_tag_name)
);
```

This allows users to answer disambiguation questions **once per file**, and the answer persists even if they later update file tags.

## Dual-Layer Disambiguation: Tagminder + Server

### The Architecture

Disambiguation logic should live in **both** Tagminder and the music server:

- **Tagminder Users (VIP Lane):** Solve disambiguation at tagging level → Tagminder populates synthetic MBIDs and retains user decisions → Server encounters clean, fully-resolved tags → ⚡ Blazing fast ingestion
- **Non-Tagminder Users:** Raw/messy tags → Server handles disambiguation via UI → User resolves via server dashboard

### User Workflow Divergence

```
[User Type A: The Perfectionist]
Files ➔ Processed by TAGMINDER 
    ➔ Explicit MBIDs / Synthetic UUIDv5s Written
    ➔ Server Scans
    ➔ ⚡ Blazing Fast, Zero Questions

[User Type B: The Casual Listener]
Files ➔ Raw/Messy Tags Only
    ➔ Server Scans
    ➔ Synthetic UUIDv5 Context Generated
    ➔ UI Resolution Queue
    ➔ User Solves via Server
```

### Shared Contract: Architectural Alignment

For seamless dual-layer operation, **Tagminder and Music Server must share identical logic:**

#### Rule 1: Identical Namespace for Synthetic UUIDs

Both tools must use the exact same fixed **UUIDv5 Namespace DNS/URL string**.

If Tagminder generates:
```
UUIDv5(Namespace, "The Local Jazz Band") → 8f3c2b81...
```

When the Music Server reads that tag, it recognizes it as a valid synthetic UUIDv5 and ingests it with zero processing overhead.

#### Rule 2: Standardized Custom Tag Fields

Tagminder can write operational decisions directly into extended metadata blocks, signaling to the server: "This file is already perfectly resolved, skip the guessing logic."

Custom tag headers:
```
TAGMINDER_ARTIST_IS_SYNTHETIC = 1
TAGMINDER_DISAMBIGUATION_RESOLVED = 1
```

### Server Benefits

By implementing disambiguation UI for non-Tagminder users, you create a funnel between your tools:

**Scenario:** User has a massive, un-tagged collection with 400 ambiguities detected by the server.

UI message: *"We found 400 ambiguities. You can resolve them here one-by-one, or you can run Tagminder over your library to automatically fix, embed, and permanently lock these identities into your music files."*

This protects your server's reputation as a high-fidelity playback machine while using Tagminder as the heavy-duty data refinery.

## The Agnostic Scanner Model

> **Key Insight:** The server scanner does **not** need to detect whether a file was pre-optimized by Tagminder. It only needs to look at the data payload of the tags.

**Binary Logic:**
- If IDs are present → Ingest with deterministic pipeline
- If IDs are absent → Generate synthetic fallback

### Why This Works

**Zero Vendor Lock-In:** Whether a user tags with Picard, Beets, or your advanced Tagminder build, the server processes all identifiers through the same blazing-speed pipeline.

**Deterministic Symmetry:** Because both tools use identical logic, an unmapped artist processed by Tagminder produces the exact same UUIDv5 the server would generate locally. If a user moves from "Server-resolved" to "Tagminder-tagged", IDs match 1:1, and database state never fractures.

**Failsafe Ingestion:** Empty or plain-text tags trigger the fallback mechanism automatically.

---

## Summary

The music server should be a **dumb, high-speed pipe** that:

1. **Ingests identifiers if they exist** (real MBIDs or synthetic UUIDs) with zero overhead
2. **Generates synthetic UUIDs deterministically** for unmapped contributors using UUIDv5 + normalized names
3. **Handles disambiguation contextually** by combining name + album MBID to avoid namesake collisions
4. **Persists user decisions** to immutable `track_uuid` to survive tag changes
5. **Maintains an abstraction layer** (contributor_id → real MBID or synthetic UUID) for future resolution
6. **Marks synthetic entities explicitly** so they can be audited and externally resolved
7. **Treats all incoming data agnostically**, regardless of source or prior optimization

This architecture enables a progressive enhancement model where Tagminder becomes the "VIP lane" for power users while keeping the server resilient for everyone else.
